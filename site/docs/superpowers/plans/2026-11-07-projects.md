# Projects Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Builders can save parcels from search into projects, track them on a `/projects` board by stage, and work each project on its own page, which has its lots, notes, the SB 684 checklist, the 60-day review clock, and an activity log.

**Architecture:** The stage, checklist, and clock rules are pure functions in `lib/projects/`, and they're unit-tested. A service module (`app/api/trpc/project-service.ts`) loads and checks ownership, applies those rules, and writes to Prisma in transactions. The `projects` tRPC router is a thin layer over it, so the AI branch's `save_to_project` and `update_project` tools can call the same service. The pages are client components that use `useTRPC()` and TanStack Query.

**Tech Stack:** Next.js 16 (App Router), tRPC 11 with `@trpc/tanstack-react-query`, Prisma 7 against Neon Postgres, zod 4, MapLibre GL, Vitest, Tailwind 4.

**Spec:** `site/docs/superpowers/specs/2026-11-07-projects-design.md`. The executor reads it alongside this plan. All paths below are relative to `site/`.

## Global Constraints

- Every project read and write is scoped to the signed-in user. A missing project and another user's project both return `NOT_FOUND`, never `FORBIDDEN`. Use `assertOwner(user, { userId: row.user_id })`.
- Checklist items never start checked from parcel data. Keep the "Screening estimate, not legal advice." line wherever parcel eligibility shows.
- Stages, in order: Found, Screening, Owner outreach, Feasibility, Application submitted, Approved, Funded, Under construction. A new project starts in Found.
- Review deadline = submission date + 60 calendar days. Amber at 15 or fewer days left, red once the deadline has passed.
- Don't use `window.confirm`, `alert`, or `prompt`. Confirm steps happen in the page.
- Don't change `../pipeline/`. A pipeline reload emptying projects is a known, accepted issue.
- Schema changes are additive, so use `pnpm exec prisma db push` and never pass `--accept-data-loss`. Check which database `DATABASE_URL` points at first. It should be the Neon `dev` branch.
- New pages call `requirePageUser()` and are under the `proxy.ts` matcher.
- Hooks go in `lib/hooks/`, one per file. Shared components go in `components/`. Keep comments minimal (see `CLAUDE.md`).
- Before writing page code, read the relevant guide in `node_modules/next/dist/docs/` (per `AGENTS.md`). In Next 16, `params` is a `Promise`.
- Not in scope: funding, the AI assistant, dragging cards, sharing, uploads.

## Review Focus

1. **Day boundaries in the clock.** A builder in California at 9pm on day 45 must see "15 days left" (amber), not the UTC date. "Today" is computed in `America/Los_Angeles`. *Pinned in Task 1.*
2. **Moving to Application submitted with no date.** If item 8 is unchecked and no date is given, the server rejects with `BAD_REQUEST` and writes nothing. If item 8 is already checked, the move needs no date. *Pinned in Task 2 and Task 4.*
3. **Saving a lot that's already in the project, or an APN that isn't in `parcels`.** Both are skipped without an error, and only lots actually added are logged. *Pinned in Task 4.*
4. **Another user's project id in any procedure** returns `NOT_FOUND` and writes nothing. *Pinned in Task 4.*
5. **Blank or whitespace-only project names** are rejected, and names are trimmed. *Pinned in Task 4.*

### Task 1: Stages, checklist items and the review clock

**Files:**
- Create: `lib/projects/stages.ts`, `lib/projects/checklist.ts`, `lib/projects/review-clock.ts`
- Test: `tests/lib/projects/review-clock.test.ts`, `tests/lib/projects/stages.test.ts`

**Interfaces:**
- Produces:
  - `PROJECT_STAGES = ["found","screening","owner_outreach","feasibility","application_submitted","approved","funded","under_construction"] as const`; `type ProjectStage = (typeof PROJECT_STAGES)[number]`; `STAGE_LABELS: Record<ProjectStage,string>` ("Found", "Screening", "Owner outreach", "Feasibility", "Application submitted", "Approved", "Funded", "Under construction"); `stageIndex(stage: ProjectStage): number`; `isApprovedOrLater(stage): boolean`.
  - `CHECKLIST_ITEMS: readonly { key: ChecklistKey; label: string }[]` with keys `zoning`, `size_urban`, `min_parcel_size`, `max_parcels_homes`, `tentative_map`, `owner_authorization`, `occupancy_affidavit`, `application_submitted`, in that order. The labels are the spec's text exactly (design doc, "SB 684 checklist"). `type ChecklistKey`. `SUBMITTED_ITEM: ChecklistKey = "application_submitted"`.
  - `REVIEW_DAYS = 60`, `WARNING_DAYS = 15`.
  - `todayInLA(now: Date): string`, which returns `YYYY-MM-DD` using `Intl.DateTimeFormat("en-CA", { timeZone: "America/Los_Angeles" })`.
  - `addDays(day: string, n: number): string`, which works on `YYYY-MM-DD` with UTC arithmetic.
  - `reviewClock(input: { submittedOn: string; today: string; stage: ProjectStage; approvedOn: string | null }): ReviewClock` where
    `type ReviewClock = { kind: "running"; deadline: string; daysLeft: number; tone: "normal" | "warning" } | { kind: "missed"; deadline: string; daysOver: number } | { kind: "stopped"; deadline: string; approvedOn: string; daysBeforeDeadline: number }`.
    The clock is `stopped` when `isApprovedOrLater(stage) && approvedOn !== null`. Otherwise it's `running` when `daysLeft >= 0` (tone `warning` when `daysLeft <= 15`), and `missed` when `daysLeft < 0`.
  - `clockLabel(clock: ReviewClock): string`

### Task 2: Stage and checklist rules, and activity text

**Files:**
- Create: `lib/projects/rules.ts`, `lib/projects/activity.ts`
- Test: `tests/lib/projects/rules.test.ts`, `tests/lib/projects/activity.test.ts`

**Interfaces:**
- Consumes: Task 1's stages, checklist, and `ProjectStage`.
- Produces:
  - `class ProjectInputError extends Error { code: "SUBMISSION_DATE_REQUIRED" | "NOT_SUBMITTED" }`
  - `type ProjectState = { stage: ProjectStage; submittedOn: string | null; approvedAt: Date | null; submittedItemDone: boolean }`
  - `type ActivityKind = "created" | "stage_changed" | "parcel_added" | "parcel_removed" | "item_checked" | "item_unchecked" | "submitted_date_changed"`
  - `type ActivityEntry = { kind: ActivityKind; data: Record<string, string | number | null> }`
  - `type Plan = { project: Partial<{ stage: ProjectStage; submittedOn: string | null; approvedAt: Date }>; items: { key: ChecklistKey; done: boolean }[]; activity: ActivityEntry[] }`
  - `planStageChange(state: ProjectState, to: ProjectStage, opts: { submittedOn?: string; now: Date }): Plan`
  - `planChecklistChange(state: ProjectState, key: ChecklistKey, done: boolean, opts: { submittedOn?: string; now: Date }): Plan`
  - `planSubmittedOnChange(state: ProjectState, submittedOn: string): Plan`, which throws `NOT_SUBMITTED` when item 8 isn't done
  - `describeActivity(entry: ActivityEntry): string`

Rules (from the design doc):
- Changing to the current stage returns an empty plan (no changes, no activity).
- Moving to `application_submitted` with item 8 not done requires `submittedOn`, or it throws `SUBMISSION_DATE_REQUIRED`. With a date, the plan sets `submittedOn`, checks item 8, and logs `stage_changed` then `item_checked`. With item 8 already done, it changes only the stage.
- Moving from a stage below Approved to Approved or any later stage sets `approvedAt: now`. Moving back down keeps `approvedAt`. Moving between two approved-or-later stages doesn't change it.
- Moving out of Application submitted leaves item 8 and the date alone.
- Checking item 8 requires `submittedOn`, or it throws `SUBMISSION_DATE_REQUIRED`. Unchecking it sets `submittedOn: null` and logs `item_unchecked`. It never changes the stage, because the "move stage?" offer happens in the UI.
- Checking or unchecking an item to the state it's already in returns an empty plan.
- Activity data: `stage_changed {from,to}`, `item_checked/unchecked {key}`, `submitted_date_changed {from,to}`, `parcel_added/removed {apn,address}`, `created {parcelCount}`.

  });

it("needs no date when item 8 is already checked", () => {

**Interfaces:**
- Consumes: Task 2's plans and `ProjectInputError`, Task 1's constants, and Task 3's models.
- Produces:
  - In `parcels.ts`: `export const PARCEL_RESULT_COLUMNS: Prisma.Sql`. This is the existing select list, from `apn` through `lat`, and `search` keeps using it.
  - Service, where every function takes `user: { id: string }` first and throws `NotFoundError` or `ProjectInputError`:
    `listProjects(user): Promise<BoardProject[]>`, `getProject(user, id): Promise<ProjectDetail>`, `projectOptions(user, apn): Promise<{ id: string; name: string; hasParcel: boolean }[]>`, `createProject(user, { name, apns? }): Promise<{ id: string }>`, `addParcels(user, id, apns): Promise<{ added: string[] }>`, `removeParcel(user, id, apn)`, `renameProject(user, id, name)`, `setNotes(user, id, notes)`, `setStage(user, id, stage, submittedOn?)`, `setChecklistItem(user, id, key, done, submittedOn?)`, `setSubmittedOn(user, id, submittedOn)`, `deleteProject(user, id)`.
  - `type BoardProject = { id; name; stage: ProjectStage; lotCount: number; homes: number; checklistDone: number; submittedOn: string | null; approvedOn: string | null; updatedAt: Date }`. `homes` is the sum of `max_homes`, with nulls counted as 0.
  - `type ProjectDetail = { id; name; stage; notes; submittedOn: string | null; approvedOn: string | null; parcels: ParcelResult[]; checklist: { key: ChecklistKey; label: string; done: boolean }[]; activity: { id: string; kind: ActivityKind; data: ActivityEntry["data"]; createdAt: Date }[] }`. `approvedOn` is `todayInLA(approved_at)`. The checklist is in `CHECKLIST_ITEMS` order, and activity is newest first.
  - Router `projects` with procedures `list`, `get {id}`, `options {apn}`, `create {name, apns?}`, `addParcels {id, apns}`, `removeParcel {id, apn}`, `rename {id, name}`, `setNotes {id, notes}`, `setStage {id, stage, submittedOn?}`, `setChecklistItem {id, key, done, submittedOn?}`, `setSubmittedOn {id, submittedOn}`, `delete {id}`. Every one is `protectedProcedure`.
  - zod: `name: z.string().trim().min(1).max(120)`, `notes: z.string().max(20_000)`, `submittedOn: z.iso.date()`, `stage: z.enum(PROJECT_STAGES)`, `key: z.enum(CHECKLIST_ITEMS.map(i => i.key))`, `apns: z.array(z.string()).min(1).max(50)`.
  - Error mapping in the router: `NotFoundError` becomes `NOT_FOUND`, and `ProjectInputError` becomes `BAD_REQUEST` with `message = error.code`. The UI reads `SUBMISSION_DATE_REQUIRED` from the message.

Service behavior:
- Load the project and run `assertOwner(user, { userId: project.user_id })` before any write. Do each write in `db.$transaction(async (tx) => …)`. It applies the plan's project fields, updates `ChecklistItem` rows (`done_at` set to now or null), inserts activity rows in plan order with timestamps 1 ms apart so they sort correctly, and bumps `updated_at`.
- `createProject` creates the project, all eight checklist rows (unchecked), the parcel links, and one `created {parcelCount}` activity.
- `addParcels` keeps only APNs that exist in `parcels` and aren't already linked. It links them and logs one `parcel_added {apn,address}` for each.
- `removeParcel` logs `parcel_removed` with the parcel's address.
- `rename` and `setNotes` don't write activity.
- `getProject` loads parcels with `db.$queryRaw` using `SELECT ${PARCEL_RESULT_COLUMNS} FROM parcels JOIN project_parcels pp USING (apn) WHERE pp.project_id = ${id} ORDER BY pp.created_at`.
